Temuan source yang akan direproduksi: form/controller create/update pembayaran manual membatasi jumlah minimal0, tetapi tidak membatasi kapasitas `DECIMAL(12,2)` yang sama pada pembayaran, invoice dan keuangan. Nilai maksimum penyimpanan positif adalah9999999999.99, bukan batas bisnis baru. SQLite tidak menegakkan kapasitas tersebut. Risiko yang belum dianggap fakta produksi: input di atas kapasitas masuk ke jalur penyimpanan MySQL dan menjadi error DB alih-alih validasi yang bisa diperbaiki operator.

Kriteria penerimaan: create/update manual menolak nilai melebihi kapasitas dengan error field jumlah sebelum file/payment/invoice/ledger berubah; nilai0, nominal biasa dan maksimum tetap diterima sesuai aturan lama; maksimum tersimpan persis sampai invoice dan approval retry satu income pada MySQL nyata. Penggantian bukti pada input invalid tidak menghapus bukti lama/meninggalkan file baru. Form memberi batas yang selaras tanpa paragraf UI baru. Test negatif nonnumeric/negative tetap ditolak. Tidak mengubah aturan pembulatan/pecahan, nominal existing, approval, coverage, izin, transaksi, schema atau endpoint publik/generasi tagihan lain. Jalur lain dicatat untuk tinjauan lanjutan, bukan diklaim aman oleh fix sempit ini.

Peningkatan operasional adalah pemulihan kesalahan input sebelum write, bukan fitur terpisah yang ditumpuk di atas bug. PR terpisah berbasis #13; tidak mengubah PR sebelumnya atau merge sebelum gate staging/UAT. Reproduksi dan hasil final dicatat di bawah setelah dijalankan; tidak ada data/notifikasi produksi.

## Reproduksi dan perubahan

Tes baru sebelum fix: lokal3tes/17assertion,2gagal karena create/update menerima `10000000000.00` dengan302 alih-alih422. Positive zero/max lulus. Source test-only `7074caf9030317d8661a93c411b0f4371423c9bc`, tree `d0965ec19f1cf292eb2367a06699740e03cc1a71`, [CI39250144789](https://github.com/mvnz/kostSan/actions/runs/39250144789) mereproduksi kedua kegagalan backend dan MySQL8.4.11 REPEATABLE-READ `SQLSTATE22003/1264 Out of range value for column jumlah` pada controller create aktual. Browser dilewati CI karena dependency backend merah, bukan dianggap lulus. Tidak ada pengujian pada produksi.

Fix sempit: tambah max sesuai DECIMAL(12,2) pada validasi create/update manual, pesan field Indonesia; HTML max, label terhubung, inline feedback dan aria invalid/describedby. Validasi tetap sebelum transaksi/private upload. Tidak mengubah schema/transaksi/approval atau menormalisasi/memotong nominal diam-diam. Tes error memakai fake storage; MySQL nyata menguji nilai maksimum persis pada pembayaran/invoice/ledger dan approval dua kali. Browser baru menguji native range overflow, server validation saat native validation sengaja dilewati oleh tes, nilai form bertahan, lalu koreksi berhasil pada tiga viewport.

Selama green lokal pertama, snapshot test update sempat gagal karena membandingkan model baru yang belum di-reload (tipe/key/default raw berbeda) dengan hasil DB. Koreksi fixture mengambil snapshot DB melalui fresh sebelum aksi, tanpa mengurangi assertion kesetaraan penuh. Ini kesalahan fixture, bukan bug aplikasi baru. Sesudahnya3tes/80assertion lulus. Hasil suite/CI final menunggu pengulangan setelah perubahan terakhir.
